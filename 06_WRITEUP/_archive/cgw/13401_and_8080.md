## 摘要

1. **13401/tcp 是一个"接受即关闭、从不读、从不写"的空监听**。我们用一个"把数据塞进三次握手第三个 ACK"的
   实验，配合抓包，证明应用层从未 `read`：有数据在接收队列时服务端先 `ACK` 再 `RST`，无数据时发 `FIN`。
   任何应用层协议（TLS/DoIP/SLCAN/socketcand/SOME-IP/自定义长度前缀……）都要求先 `read`，
   所以**不是"协议猜错"，而是该 listener 不承载任何可交互协议**。靶场 09:5x 重启迁移到 10.226.193.2 后，
   同一套实验**逐字节复现**（`0520`）。
2. 8080 是 **Go net/http + Go 1.22+ ServeMux 的存活探针桩**，只注册 `/healthz`；本轮补齐 14 条协议级
   怪点（`OPTIONS *`、绝对 URI、CONNECT、CL+TE 走私、duplicate Host、WebSocket Upgrade、8KB 路径……），
   **无新路由、无升级、无转发面**。
3. 结合题面"经 13400 诊断例程**开启** CAN FD 桥 13401"，最合理的解释是：**13401 是一扇关着的门**——桥未开时
   listener 表现为 accept-close，开桥动作应让它开始 read/回帧。开桥例程大概率在 cgw-doip 发现的 `0x1220`
   （唯一实现 `0x31` 的节点，安全门锁死），凭据需来自 DoIP 之外。两者对 T03 的 flag 均无直接产出。

## 1. 13401：从"未知协议"到"空监听"的取证过程

### 1.1 起点（前三分钟的观察）

- `connect()` 成功，但**不发任何数据**时 25.6 ms 内收到 FIN（recv 返回 `b''`）。
- 发任意字节后有时 `RST`（客户端 WinError 10053），有时 `FIN`——这个"随机性"是关键线索：
  它说明 FIN/RST 不是协议拒绝，而是**数据与 close 的赛跑**。

### 1.2 关键实验：把数据放进第三个 ACK

普通 socket 无法控制"数据是否在服务端 accept 之前到达"。用 scapy 自建握手：

```
SYN  ──────────────────────────────►   SYN-ACK
ACK + 16B 0x00  ───────────────────►   ③ 数据在 accept 返回前进入接收队列
                                       ④ 服务端 A(ack=seq+16)   ← TCP 层确认收到
                                       ⑤ 同一毫秒 R(ack=seq+16) ← close() 时队列有未读数据
```

Linux/Windows 内核语义：`close()` 时接收队列仍有未读数据 ⇒ 发 **RST**；数据已被应用读走 ⇒ 正常 **FIN**。
因此 `ACK→RST` 是"应用没读过这 16 字节"的**充分证据**。对照组（第三 ACK 不带数据）收到干净 **FIN**。

抓包（`03_EVIDENCE/cgw/0511_13401_packetlevel.txt`，相对时间单位秒）：

| 实验 | 客户端 | 服务端 |
|---|---|---|
| A 只建连 | `S(-0.0327) → A(-0.0004)` | `SA(-0.0005)`，**`FA(+0.0256, len 0)`** |
| B 建连后发 16B | `PA(0)` 重传 `PA(+0.2426)` | **`R(+0.2685)`**（无 FIN） |
| C 16B 在第三 ACK | `A+data(+7.8139)` | **`A(+7.8406, ack=seq+16)` + `RA(+7.8406)`** |
| D 第三 ACK 无数据 | `A(+11.8526)` | **`FA(+11.8781, len 0)`** ×4（我们未回 ACK） |

> 抓包里小包尾部 6 字节 `000000000000` 是 Ethernet 最小帧填充，不是数据（SYN-ACK 的 2 字节 `0000` 同理）。

**交叉验证**：另一组独立测试了 `13401_bytes.json` 的 **256 个单字节值**（`FIN=156 / RST=100`，
**0 个回包**）与 `sec04/13401_framing.jsonl` 的 27 种 framing（0 回包），与本组结论一致。

### 1.3 排除矩阵（细节见 HYP-cgw-03）

| 类别 | 试过 | 结果 |
|---|---|---|
| 服务端先发 | 0 数据保持 3–5 s | 25.6 ms 就 FIN，无 banner |
| DoIP 状态 | routing activation(0x0E00→0x10)、UDS 0x10 03、源端口 13400、两实例 | 全 FIN，不变 |
| 时间窗 | 60 s/20 次 | 20/20 FIN |
| TLS | ClientHello | EOF（且 TLS 服务端也必须先 read） |
| 车联网桥 | SLCAN、ELM327、socketcand、cannelloni、SOME/IP-SD、MQTT、DoIP on 13401、ISO-TP、Modbus/TCP | 20 条全无回包 |
| 自定义 | 1/2/4B LE/BE 长度前缀、AA55/CANFD/CANGW 魔数、ASCII UDS | 全无回包 |
| TCP 指纹 | 8080/13400/13401 SYN-ACK | TTL 63 / win 64240 / MSS 1386，三者完全一致 ⇒ 同机同栈 |
| UDP | 13400 DoIP ident、13401 空包/CANGW/8×00 | 无回包；**但关闭端口 34777 也无 ICMP** ⇒ 探测法失效，见 §1.4 |

### 1.4 两个"不能下结论"的点（明确写出，防止过度断言）

- **UDP 13401**：本 vantage 上 ICMP port-unreachable 被过滤（确定关闭的 34777/udp 同样静默），
  因此"无回包"无法区分 open / filtered / closed。DoIP 规范要求 13400/udp 对 vehicle identification
  有响应，实测也没有——这更像链路/策略拦截，而不是"没有 UDP 服务"。
- **源 IP 白名单**：若 listener 只对内网/车辆网段放行，外部客户端永远被 close。TCP 伪源 IP 需要能收到
  SYN-ACK（被伪造地址收），没有内网跳板就无法完成握手，故本 vantage 不可测。

### 1.5 结论

```
13401/tcp  ≡  accept(); close()   // 无 read、无 write
```

- 对 CTF 而言：**在"桥未开"状态下它不是入口**；任何客户端首帧都不会被读到（不是协议猜错）。
- 与 F1A0=`07E0 07E8 07E1 07E9`（doip 组结论）的关系：这四个 ID 是桥的**目标清单**，
  桥不可交互时清单无从使用；桥一旦打开，清单就是第一组要打的 CAN ID（见 §6 行动手册）。
- 与题面"诊断例程开启桥"结合，主解释是**关着的门**：开桥动作应让 listener 开始 read/回帧（§5 的监测器即判据）。
  若桥开之后仍 accept-close，才需要怀疑内网白名单/进程已死的旁路解释。

### 1.6 新实例复现（10.226.193.2）

09:51 旧 IP 全部不可达的**真实原因是靶场重启迁移**（不是 VPN 掉线）：新 CGW = `10.226.193.2`，
VIN 变为 `CV622697F82A936A1`，并多出第二个 UDS 节点 `0x1220`（cgw-doip 发现）。新实例上：

| 实验 | 新实例观测 | 与旧实例 |
|---|---|---|
| A 只建连 | SYN-ACK 后 **+26 ms `FA`**，0 字节 | 一致 |
| B 建连后发 16B | 先 `FA ack=our_syn+1`（未 ACK 16B，FIN 先于数据），随后 `R` | 一致 |
| C 16B 在第三 ACK | `A(ack=seq+16)` → 同毫秒 **`RA`** | **一致：仍未 read** |
| D 第三 ACK 无数据 | 干净 `FA` ×4 | 一致 |

证据：`03_EVIDENCE/cgw/0520_newenv_13401_packetlevel.txt`、`0519_newenv_10.226.193.2.txt`。
⇒ "accept-close / 从不 read"是该服务的稳定设计，跨实例不变。

## 2. 8080：Go 存活探针桩（复核结论）

- `/healthz` 对**任意方法**返回 `200 {"status":"ok"}\n`；其余路径恒 `404 page not found\n`。
- `OPTIONS *` → `200 Content-Length: 0`（Go 默认，非自定义）；`CONNECT` → 404（非代理）；
  绝对 URI 按 path 路由（Go 行为）；`Upgrade: websocket` → 普通 200（无升级）；
  重复 `Host` → 400（Go 拒绝）；`/x/../healthz` → 307 规范路径；`/healthz%00` → 404。
- 无 `Server`/CORS/Cookie；无 h2c/gRPC；无 vhost 路由（web 组 12 种 Host 已试）。
- 结论：**不存在"CANGW 转发 API"** 能让 8080 侧绕到内部 CAN 侧；handler 忽略 query/body/method。
- 补充：ecu-bridge 发现 **`/internal/audit` 是"已注册路由"**（404 但 body 是 JSON `{"error":"not found"}`，
  与 Go 默认 19B text 404 不同）。本组在新实例复核：`/healthz` 200、`/internal/audit` 404 JSON、`/internal/audit/`
  回落为 text 404（精确路径注册）；换 Host/internal、X-Forwarded-*、absolute URI 均无变化（`0530`）。

## 3. 对团队的直接价值

1. **定性止损**：13401 不是"未知协议入口"，而是"关着的门"；在开桥例程成功前，任何首帧/协议猜测都不会有响应，
   避免继续投入。
2. **判据可复用**：`第三 ACK 带数据 + 抓包` 是判断"远端是否 read 了我们的数据"的通用手法；
   比"发数据看 FIN/RST"可靠（后者会被数据/close 赛跑误导）。
3. **环境事实**：8080/13400/13401 同机同栈（SYN-ACK 指纹一致）；nmap 在本机崩溃（0xC0000005），
   全端口扫描请用 `04_SOLVE/cgw/fastscan.py`（selector 非阻塞 connect）而不是 nmap/scapy blast。
4. **开桥探针**：`04_SOLVE/cgw/watch_bridge.py` 每 10 s 一次 connect-only（1 连接/10 s），
   桥一开就打印 `STATE_CHANGE` 并退出，可作为开桥例程成功与否的独立判据。

## 6. 开桥后的行动手册（预置，桥一开就执行）

> `watch_bridge.py` 报 `STATE_CHANGE` 后按顺序做，任何一步拿到回包就停并落盘。

1. **先看有没有服务端先发的帧**：连接后 1.5 s 内任何字节都原样记录（可能是 banner/版本/协议名）。
2. **`bridge_probe.py`**：每个候选首帧一个连接，覆盖 socketCAN classic（16B）/ CAN FD（72B）、
   big-endian CAN ID、ASCII `can0 7E0#…`、candump、JSON、SLCAN、socketcand、2B/4B 长度前缀、DoIP-on-CAN。
   任一回包 → 用同一 framing 复现一次，确认不是噪声。
3. **若确认是 CAN 透传**：按 `F1A0` 的清单打 UDS：
   `0x7E0` 发 `02 10 03` → 期望 `0x7E8` 回 `50 03`；`0x7E0` 发 `03 22 F1 90` → 期望 `0x7E8` 回 VIN。
   成功后用 `0x7E0/0x7E8` 扫 DID（先 F190/F1A0/F1A3），再 `0x7E1/0x7E9` 第二组。
4. **若回包看起来是 SecOC/加密帧**：记录完整字节、时间戳与 CAN ID，交给 lead 决定是否值得做密钥推导。
5. **纪律**：`0x2E`/`0x31-01`/`0x27-02`/`0x11`/`0x14`/`0x28`/`0x34-0x38` 等写/解锁类服务
   一律先报 lead，不擅自下发；只读用 `0x22`、`0x19-02`、`0x3E 00`。
