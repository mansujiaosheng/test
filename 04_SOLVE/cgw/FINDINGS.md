## 0. 结论摘要

1. CGW 的 DoIP 实体（LA `0x1000`）是一个**只读最小实现**：只实现 `0x22`，只有 2 个 DID（VIN、4 个 CAN 诊断 ID）；`0x10/0x19/0x27/0x31/0x3E/0x2E` 等一律 `7F xx 11`。
2. **网关后面有一个第二个 UDS 节点 `0x1220`**，只能通过**功能地址 `0xE442`** 到达（整个 16 位逻辑地址空间 65536 个地址里唯一的异源响应）。它才是实现会话/安全访问/例程的那个 ECU。
3. `0x1220` 上：`10 03` 正常（`50 03`）；DID `F1A3` 存在但 `7F 22 33`（securityAccessDenied）；`0x31` 任意 RID 都是 `7F 31 33`；`0x27` 任意子功能/会话/SA 都是 `7F 27 7E`；`0x2E` 全部 65536 个 DID 都是 `7F 2E 31`；`0x23/0x19/0x3E` 都是 `7F xx 11`。
4. **安全门从 DoIP 侧无法打开**：`0x27` 的实现自相矛盾（服务存在但任何可达会话都回 0x7E，且 `0x10` 只接受 0x03），`0x2E` 写表为空，`0x31` 被安全门整体锁死。这与题面「经 13400 诊断例程开 CAN FD 桥」的叙事冲突 ⇒ 开锁凭据大概率来自 DoIP 之外（OTA 工程包 / 诊断票据），不是靠继续猜子功能。
5. `13401` 在新环境**接受 TCP 后完全静默**（DoIP/HTTP/TLS/socketcand/长度前缀/CAN 帧/换源端口/连发三次，全部 0 字节回包），符合「桥未开」的预期。

## 1. 车辆识别（自检）

**目的**：确认新环境链路与实体身份。

```
TX  ptype=0x0001 payload=""
RX  ptype=0x0004 payload=
    4356363232363937463832413933364131 1000 060000001000 000000000000 00 00
```
- `4356...4131` = `CV622697F82A936A1`（17 字节 VIN）
- `1000` = DoIP 实体逻辑地址
- `060000001000` = EID，`000000000000` = GID，`00` = further action，末尾多 1 字节 `00`（33 字节，规范 32）
- **结论**：实体 = `0x1000`，与 lead 给的 VIN 一致；链路正常。

## 2. Routing activation（含 Lead 要求的 OEM/工程模式矩阵）

**目的**：确认激活是否可被 OEM 字段/激活类型改变（工程模式假设）。

```
TX  0E00 00 00000000        (SA=0x0E00, type=0x00, reserved, 无 OEM)
RX  0E00 1000 10 00000000   tester=0x0E00 entity=0x1000 code=0x10(routing successfully activated)
```

16 组矩阵（activation type `0x00/0x01/0xE0/0xE1` × OEM 字段 `无/00000000/43563631("CV6")/FFFFFFFF`）：

- **16/16 全部 `code=0x10`**，且激活后 `22F190` 正常、`3E00` 仍 `7F3E11`、`22F1A3` 仍 `7F2233`。
- **结论**：服务端完全不校验 activation type 与 OEM 字段，工程模式无法从这里打开；这条假设证伪。

## 3. 网关 `0x1000` 的 UDS 面

**目的**：确认网关自身实现了哪些服务与 DID。

| 请求 | 响应 | 解析 |
|---|---|---|
| `10 03` | `7F 10 11` | serviceNotSupported |
| `3E 00` | `7F 3E 11` | serviceNotSupported |
| `27 01` | `7F 27 11` | serviceNotSupported |
| `19 02 FF` | `7F 19 11` | serviceNotSupported |
| `31 03 FF00` | `7F 31 11` | serviceNotSupported |
| `22 F190` | `62 F190 4356363232363937463832413933364131` | VIN |
| `22 F1A0` | `62 F1A0 07E0 07E8 07E1 07E9` | 4 个 CAN 诊断 ID（7E0↔7E8、7E1↔7E9） |
| `22 F187/F188/F189/F18A/F1A1/F186/F195/F19E/F1AF` | `7F 22 31` | 不存在 |

**全 DID 空间（0x0000-0xFFFF，65536 条）**：只有 `F190`、`F1A0` 两个正解，其余 65496 条 `7F 22 31`；38 条流水线扫描漏响应的 DID 已在干净连接上逐条复验为 `7F 22 31`。
**结论**：网关自身只读、无写服务、无会话、无安全访问；`F1A0` 是下游 CAN ID 清单而不是 DoIP 路由表（把 0x07E0 等当 TA 全部 `7F 22 31`/`7F 3E 31`，未转发）。

## 4. 第二个 UDS 节点 `0x1220`（本轮关键发现）

**目的**：穷举逻辑地址空间，看是否存在被路由的下游节点。

**发现**：向功能地址 `0xE442` 发诊断报文，响应源地址是 **`0x1220`**（不是 `0x1000`）：

```
TX  0E00 E442 3E00
RX  1220 0E00 7F 3E 11        ← 源地址 0x1220，且 0x3E 是“服务未实现”而不是“目标未知”
```

- 对 `0x0000-0xFFFF` 全部 65536 个逻辑地址做 `3E 00` 扫描：**只有 `0xE442` 一个异源**（`src=0x1220`），其余全部 `src=0x1000 + 7F3E31`；125 条漏响应已逐条复验。
- 新环境重扫 `0xE000-0xEFFF`：同样只命中 `0xE442`（`03_EVIDENCE/cgw/3248_lascan_e000_efff.jsonl`）。
- 物理寻址 `TA=0x1220` 不路由：响应仍是 `0x1000` 的 `7F xx 31`（见下表）。

### 4.1 物理 vs 功能寻址

| 目标 | 请求 | 响应 | 解析 |
|---|---|---|---|
| **物理 `0x1220`** | `22 F1A3` | `1000 0E00 7F 22 31` | 网关本地拒绝（不路由） |
| 物理 `0x1220` | `10 03` / `27 01` / `31 03 FF00` | `7F 10 31` / `7F 27 31` / `7F 31 31` | 同上 |
| **功能 `0xE442`** | `22 F1A3` | `1220 0E00 7F 22 33` | **securityAccessDenied（DID 存在）** |
| 功能 `0xE442` | `10 03` | `1220 0E00 50 03` | **扩展会话进入成功** |
| 功能 `0xE442` | `27 01` | `1220 0E00 7F 27 7E` | subFunctionNotSupportedInActiveSession |
| 功能 `0xE442` | `31 03 FF00` | `1220 0E00 7F 31 33` | 例程服务被安全门锁 |

### 4.2 `0x1220` 的服务/安全矩阵（全部实测）

| 维度 | 试验 | 结果 |
|---|---|---|
| `0x27` 子功能 | 奇/偶、`01/02/03/04/05/06/07/09/0B/11/21/41/61/81/…/FF`（128 个奇数全试 + 偶数抽样） | **一律 `7F 27 7E`** |
| `0x27` 带额外字节 | `27 01 + 00000000`、`27 02 + 0000`、`27 04 + 0000`、`27 06 + 0000` | 一律 `7F 27 7E` |
| 会话上下文 | 默认会话 / `10 03` 之后 / `10 03 + 3E 00` 之后 | 一律 `7F 27 7E` |
| tester SA | `0x0E00 / 0x0E80 / 0x0E01 / 0x0100 / 0x1000 / 0x1220 / 0xE442` | 一律 `7F 27 7E` |
| `0x10` 支持面 | `10 01/02/04/05/40/60/61/7F/81` | **全部 `7F 10 12`**；只有 `10 03` 被接受 |
| `0x31` | `31 03 <RID>`（12 个 RID：`FF00/FF01/0200/0201/0202/0203/0100/0001/0002/E000/E001/FFFF`）与 `31 01 <RID>`（6 个 RID：`FF00/FF01/0200/0203/0100/FFFF`） | **一律 `7F 31 33`**（整服务被安全门锁，与 RID 无关） |
| `0x2E` | 零数据探测（`2E <DID>`，DID 全空间 65536 个） | **一律 `7F 2E 31`**（写表为空；零数据字节 ⇒ 不可能写入） |
| `0x23` 读内存 | ALFID `14/24/44` 三种地址/长度编码 | 一律 `7F 23 11`（未实现） |
| `0x19/0x3E` | `19 02 FF`、`3E 00` | 一律 `7F xx 11` |
| DID 全空间 | `0x0000-0xFFFF` 逐条 `22 <DID>` | 只有 `F1A3` 是 `7F 22 33`，其余全 `7F 22 31`；331 条漏响应已逐条复验 |
| DID 全空间（扩展会话） | `10 03` 后 `0x0000-0xFFFF` 再扫一遍 | 结果与默认会话相同（`F1A3` 仍 `0x33`）；扫描过程中出现的 `F1A4=7F2233` 是**错位假象**，干净连接逐条复验为 `7F 22 31` |

### 4.3 结论（`0x1220`）

- 它是唯一实现 `0x10/0x27/0x31/0x2E` 的节点，DID `F1A3` 与例程服务均被安全门锁住。
- **安全门打不开是服务端实现层面的矛盾**：`0x27` 服务存在（返回 0x7E 而不是 0x11/0x31），但唯一可达的会话 `0x03` 下仍判“子功能不在当前会话”，而 `0x10 01/02` 又被拒绝（0x12）⇒ 没有任何可达会话能让 `0x27` 成功。
- 因此题面「诊断例程开 CAN FD 桥」的例程**大概率就在 `0x1220`**（它是唯一有 `0x31` 的节点），但**开锁凭据不在 DoIP 协议本身**，需要外部输入（OTA 工程包/诊断票据/seed-key 材料）。继续猜子功能、猜会话、猜 RID 都是低收益。

## 5. DoIP 协议层实现边界

| 请求 payload type | 响应 | 解析 |
|---|---|---|
| `0x0001`（无参数） | `0x0004` 33 字节 | 支持 |
| `0x0002`（EID）/`0x0003`（VIN）/`0x0007`（alive check）/`0x4001`（entity status）/`0x4003`（power mode）/`0x0000`/`0xFFFF` | `ptype=0x0000 payload=01` | DoIP generic header NACK：unknown payload type |
| `0x0005` | `0x0006` | 支持（见 §2，且不校验任何字段） |
| `0x8001` | `0x8001`/`0x8003` | 支持；实测**从不发 0x8002 正 ack** |

**结论**：服务端只实现识别 + 路由激活 + 诊断三类，其余一律 generic NACK `0x0000/01`；`0x4001/0x4003` 之前被误读为“实体状态=0x01”，实际是 NACK。

## 9. 踩过的坑（留给接手者）

1. **流水线扫描会偶发丢响应/错位**（本轮 38/331 条 DID 与 125 个 LA 出现过）：任何“无响应”必须换干净连接、单请求、≥3s 超时复验；复验后全部规整。
   - 具体案例：扩展会话下的 DID 全扫（`03_EVIDENCE/cgw/3461_didscan_extended_1220_0000_ffff.jsonl`）一度报 `F1A4=7F2233`、且 `F1A3` 反而消失；干净连接逐条复验为 `F1A3=7F2233`、`F1A4=7F2231`（默认/扩展会话都一样）。**扫描器输出的“命中”必须逐条隔离复验后才可采信。**
2. **响应延迟长尾**：网关偶发 0.8–4s 才回；判定超时不要用 0.8s。
3. **不要用“有没有响应”判目标是否存在**：网关对不认识的 TA 也回 `7F 3E 31`；判据是 `src` 与 NRC 的组合（`src=0x1000 + 0x31` = 不认识；`src=0x1220` = 真节点）。
4. **`0x4001/0x4003` 的响应是 DoIP generic NACK（ptype 0x0000 / code 0x01）**，不是实体状态，别误读成“节点类型=1”。

## 10. Round-3（04 任务接手）：全 RID 扫描与双探针 LA 重扫（2026-11-14 10:44–10:55）

Lead 的两个问题：① 开桥例程是否藏在某个**不受安全访问**的 RID 里；② 之前的 LA 全扫用 `3E 00` 探针，可能漏掉不实现 0x3E 的节点。

### 10.1 `31 01` 全 RID 扫描（0x0000-0xFFFF，65536 个）

- 请求：`0E00 E442 31 01 <RID>`；判据：非 `7F31` 开头即命中。
- 结果：**65536/65536 全部 `7F 31 33`**，无任何 `71 01`/`7F3131`/`7F3113`。
- 证据：`03_EVIDENCE/cgw/3556_ridscan_3101_0000_ffff.jsonl`
- 结论：安全门是**服务级**的，先于 RID 校验 ⇒ RID 空间无法被枚举出“存在哪些例程”。

### 10.2 `31 03`（requestRoutineResults，只读）全 RID 扫描

- 结果：**65536/65536 全部 `7F 31 33`**，同上。
- 证据：`03_EVIDENCE/cgw/3655_ridscan_3103_0000_ffff.jsonl`

### 10.3 `31 01 <RID> + 1..8 字节参数`

- 对 `0x0000-0x0FFF` 4096 个 RID × 长度 1..8 全测：**全部 `7F 31 33`**（若长度校验先于安全门，应出现 `13`）。
- 证据：`03_EVIDENCE/cgw/3658/3661/3664/3667/3670/3673/3676/3679_ridscan_3101pN_0000_0fff.jsonl`
- 结论：长度校验也不先于安全门；带参探测无法反推 RID 存在性。

### 10.4 双探针重扫全 LA 空间（回应“3E 探针漏节点”的假设）

| 探针 | 65536 个 LA 中的非基线响应 | 结论 |
|---|---|---|
| `10 03` | `0x1000`→`7F1011`；`0xE442`→src `0x1220` `5003` | 只有 2 个实体，无隐藏节点 |
| `22 F190` | `0x1000`→`62F190+CV622697F82A936A1` | 只有网关有 VIN |

- 证据：`03_EVIDENCE/cgw/3810_lascan_1003_0000_ffff.jsonl`、`3909_lascan_22f190_0000_ffff.jsonl`
- **重要细节**：`22F190` 扫描里 `0xE442` 那行被记成 `src=0x1000 / 7F2231`——单独复测时该请求的响应源其实是 `0x1220`（`03_EVIDENCE/cgw/r3_srccheck_*`）。即网关在节点慢响应时会**代答** `7F..31`（源 0x1000），这是扫描判据的一个已知干扰项；`10 03` 探针不受影响（节点立即回 `5003`）。
- 为什么之前的 `3E 00` 扫描没有漏节点：网关对不认识的 TA **自己回** `7F3E31`（不是沉默）；真正沉默的地址会记为“空响应”，而 125 个空响应地址已用干净连接逐条复验为 `7F3E31`。因此“3E 探针漏掉沉默节点”的假设不成立，本轮 `10 03`/`22F190` 双探针重扫进一步证实。

### 10.5 `10` 全子功能（0x00-0xFF）与带参会话

- `10 00-FF` 256 个子功能：只有 `10 03`→`5003`，其余 255 个全 `7F1012`。
- `10 02/03/82/83 + 尾随字节`：全 `7F1012`（尾随字节使请求非法）。
- 结论：0x1220 的会话面只有 `10 03` 一条路。

### 10.6 Round-3 总结

- 隐藏节点不存在（双探针全空间一致）。
- 开桥例程无法通过 RID 枚举找到：安全门在 RID 校验之前，且没有任何 RID/参数组合绕过。
- 打开 `0x1220` 只剩一条路：**拿到能通过 `0x27` 的凭据/算法**（工程包里的 `firmwareCredential` 是否就是它，需要 Lead 提供值来试 `27 02`），或找到厂商侧另一条写通道（当前 DoIP 面不存在）。
