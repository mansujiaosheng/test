## 已穷尽的尝试（全部否定）

### A. 0x27 子功能与载荷
- `0x27 0x00..0xFF` 全部 256 个子功能 → 恒 `7F 27 7E`
- 每条连接只发一次（排除状态污染）→ 仍 `7E`
- 默认会话 / `10 03` 后 / `10 03`+3E 后 → 均 `7E`
- `27 <sub> + 完整40B票据`（256 组合）→ 全 `7E`
- `27 01 + nonce(16)` / `+ tag(16)` / `+ exp` → 全 `7E`
- `27 02 + 票据` → `7E`

### B. 2E 写入（WriteDataByIdentifier）
- cgw-doip 全 65536 DID + 零数据 → 全 `7F 2E 31`
- `2E F1A3 + 票据(40B)` / `2E F190 + 票据` / `2E F1A0 + 票据` → 全 `31`
- 推论：2E 写表为空，票据不可能走这条路

### C. 31 RoutineControl
- `31 01 <RID>` × 12 个 RID → 全 `7F 31 33`
- `31 01 <RID> + 票据` → 仍 `33`（安全优先于 RID 校验）

### D. DoIP RoutingActivation 层
- activation type: `0x00/0x01/0x02/0xE0/0xE1/0xFF` → 全部 code `0x10`（**网关不校验 type**）
- OEM 4 字节: `00000000 / FFFFFFFF / "CV6!" / 01000000` → 全部 `0x10`
- **11 字节 RA（含第 8-11 自由 4 字节）× 票据全部 37 个 4 字节切片 + exp/tag/nonce/zero/ff → 27 恒 `7E`**
- RA 载荷长度语义：仅 7 和 11 字节被接受，其余 → genericNack `0x04`（incorrect length）
- RA 的 4 字节额外字段**不回显**（响应恒 `0E001000 10 00000000`）
- tester SA 扫描（262 个值，含 0x0E00/0x1220/0xE442/0x07E0/0x07E8 等）→ RA 全部 code `0x10`，**网关不校验 SA**

### E. DoIP 报文层
- ptype 0x0001/0x0005/0x0007/0x4001/0x4003/0x8001/0x8002/0x8003/0xE001/0xE002/0xF001 载票据 → 全 genericNack `0x01` 或落到 UDS 被当服务号
- 诊断报文 SA×TA 矩阵（0x0E00/0x1220/0xE442 × 0xE442/0x1220/0x1000）载票据 → 首字节被当服务号
- ACK 请求变体（前缀 0x00/0x01、后缀 0x01、独立 0x8002）→ 全否

### F. 地址空间
- 全 65536 个 LA × `3E00` → 仅 `0x1000`（`7F3E11`）与 `0xE442`→`0x1220`（`7F3E11`）两个异源
- 扫描中 **125 个空响应地址**（`0x100E`、`0x47C0–0x47FF`、`0x4BC0+`…）用 `10 03` 与 `22F190` 重测 → **全部无响应**
- 功能地址邻域 `0xE440–0xE460` + `0xE400/0xE480/0xE4FF/0xE500` → 只有 `0xE442` 可达
- `0x1220` 的 DID 全空间：只有 `F1A3`（`33`），其余全 `31`

### G. 主机侧
- C_GW/T-BOX/别名 三台 8080：仅 `/healthz`（含 `/api/v1/bridge*`、`/canfd`、`/isotp`、`/diag/*`、`/security/*` 等 55 条路径，GET+POST 全 404）
- 8443 全站只有 `POST /api/v1/diag/session` 一个路由（1587+1773 条路径三轮扫描）
- TSP `/graphql` 不感知票据（纯 `variables.vin` 匹配器）
- 13401：桥未开，accept-then-close；明文 HTTP / TLS / DoIP / CAN 帧 / 长度前缀 / socketcand 全 0 回包

### H. 票据 tag 算法
- 用 fw 逆向出的 `0x08000668`（8 字节 keyed hash，常量 `0xA5A5A5A5`/`0x9E3779B9`/`0xC=e224dd2bb23a15b8`）暴力匹配 tag[0:8]/tag[8:16]：
  key 候选 8 组（flash id / 派生 KEK / unwrap 24B 各切片 / imgsha 切片）× msg 候选 6 组 × 全偏移 → **0 命中**
- ⇒ tag 的服务端密钥不在我们能算的范围（或算法形态不同）

## 关键矛盾（这是我认为需要设计输入的原因）

题面说「票据绑定后才能用 `27`」。但实测 `27` 返回的是 **`7E`（子功能在当前会话不支持）**，
而不是 `33`（安全访问被拒）或 `0x22`（条件不满足）。

`7E` 的语义是「**这个子功能号在当前会话根本不存在**」——它发生在**子功能派发之前**，
根本还没走到「检查票据」那一步。这与「缺票据」的假设矛盾。

同时 `22 F1A3` 和 `31` 都返回 `33`——说明**安全访问机制本身是存在的**，
只是 `27` 这个入口对任何子功能都不可用。

## 我判断的三种可能

1. **`0x1220` 的 `0x27` 是占位/未实现**，真正的 SecurityAccess 在开桥后访问的 BMS/VCU 上。
   若如此，04 与 05 的顺序应反过来：**先开桥**（但开桥又需要 31，31 被锁）——死锁，除非开桥有不需要安全访问的路径。
2. **session 不是 `10 03`**：`27` 只在某个我未进入的 session 存在。但 `10 01/02/04/05/40/60/61/7F/81` 全回 `12`，
   唯一成功的是 `03`。除非存在**非标准 session 编号**或**需要先满足某条件才能进 02**。
3. **票据绑定在 T-BOX 侧完成**，T-BOX 把「已解锁」状态透传给 CGW，而这一步我没触发成功
   （`POST /api/v1/diag/session` 只是发票，可能还需要另一个动作消费它）。
