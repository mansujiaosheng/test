# 13401/tcp —— "CAN FD 桥"候选：目标画像与实测行为

采集者：cgw（task-T03 13401+8080）｜时间：2026-11-14 09:17–10:03 CST
来源：**旧环境** 10.229.221.2 / 10.230.164.4（09:17–09:48）＋**新环境** 10.226.193.2（10:02 起，靶场重启后迁移）

> **环境变更（重要）**：09:51 旧 IP 全部不可达，不是 VPN 掉线，而是靶场重启后 CGW 迁到
> **10.226.193.2**（cgw-doip 09:5x 发现，VIN 变为 `CV622697F82A936A1`，并多出第二个 ECU `0x1220`）。
> 新实例上 13401 行为**与旧实例逐字节一致**（见 §2.1，证据 `0520`）。

## 0. 一句话结论

**该端口是一个"accept 后立刻 close、从不 read、从不 write"的空监听**。包级证据（第三个 ACK 携带 16B →
服务端先 ACK 这 16B，再同毫秒 RST；无数据时则干净 FIN）证明应用层一个字节都没读。任何应用层协议
（TLS / DoIP / SLCAN / socketcand / SOME-IP / 自定义长度前缀……）的握手都要求先 read，因此**从外部
客户端看，这个端口不可能承载任何可交互协议**。

结合题面「经 `<cgw>:13400` 诊断例程**开启** CAN FD 桥 `<cgw>:13401`」，最合理的解释是：
**这是一扇关着的门**——桥未开时 listener 表现为 accept-close；开桥动作应让它的行为改变（开始 read/回帧），
而不是去找另一个协议或另一个端口。开桥例程大概率在 cgw-doip 发现的 `0x1220`（唯一实现 `0x31` 的节点），
而其 `0x27/0x31` 被安全门锁死 → 凭据需来自 DoIP 之外（TSP/T-BOX/OTA 工程包）。
即"13401 不可交互"是**当前状态**的属性，不排除被正确例程打开后变成可交互。

## 2. 包级判定实验（决定性）

工具：scapy + Npcap，抓包在 OpenVPN TAP（`\Device\NPF_{42C6004D-…}`）。
原始记录：`03_EVIDENCE/cgw/0511_13401_packetlevel.txt`，pcap：`0508_13401_session.pcap`。

| 实验 | 客户端行为 | 服务端回包 | 解释 |
|---|---|---|---|
| A | 建连后**不发任何数据**，保持 3 s | SYN / SYN-ACK / 我方 ACK 后 **+25.6 ms FIN**，0 字节载荷 | accept 后立刻 close；无 banner、不等待 |
| B | 建连后立刻发 16×`00` | 服务端**没有 FIN**，只有 **RST**（约 +268 ms，等我们数据到达后） | close 时接收队列里已有未读数据 → 内核发 RST |
| C | scapy 自建握手，**第三 ACK 携带 16×`00`**（数据在 accept 返回前入队） | 服务端先 `A ack=seq+16`（TCP 层确认收到），**同一毫秒 `RST+ACK`** | **决定性**：应用已 close 且未 read 这 16B |
| D | scapy 自建握手，第三 ACK 不带数据（对照） | 干净 **FIN**，重传 3 次（因我们未回 ACK） | 无数据 → 正常 close |

推论链：
1. 无数据 → FIN；有数据在队列 → RST。两种路径都不含任何服务端数据。
2. TCP 层 ACK 了 B/C 的发送（说明不是链路丢包），但应用层 close 时数据仍未读 → **read 从未发生**。
3. 既然 read 从不发生，**任何需要客户端先发首帧的协议都不可能被解析**；服务端也从未 write，排除"服务端先发 banner"。
4. 因此 13401 当前对我们是**死端**，不是"协议猜错"。

### 2.1 新环境（10.226.193.2，靶场重启后）复现

同一套实验在新实例上逐字节复现（`03_EVIDENCE/cgw/0520_newenv_13401_packetlevel.txt`）：

| 实验 | 新实例（10.226.193.2）观测 | 与旧实例 |
|---|---|---|
| A 只建连 | SYN-ACK 后 **+26 ms `FA`**（0 载荷），recv 返回 0 字节 | 一致 |
| B 建连后发 16B | 服务端先 `FA ack=our_syn+1`（**未 ACK 我们的 16B**，说明 FIN 在数据到达前已发），随后 `R` | 一致（旧环境该场景 FIN/RST 取决于赛跑） |
| C 16B 在第三 ACK | `A(ack=seq+16)` → 同毫秒 **`RA(ack=seq+16)`** | **完全一致：仍未 read** |
| D 第三 ACK 无数据 | 干净 `FA`，重传 3 次 | 一致 |

⇒ "accept-close / 从不 read"是该服务的**稳定设计**，不是旧实例的偶发现象；换环境后行为不变。

## 4. UDP 13401

| 探测 | 结果 |
|---|---|
| `13401/udp` 空包、`CANGW`、8×`00`、DoIP ident | 全部无回包 |
| `13400/udp` DoIP vehicle identification（规范要求有响应） | 无回包 |
| **对照：确定关闭端口 34777/udp** | **同样无 ICMP port-unreachable** |

结论：本观测点上"无回包"不能区分 open / filtered / closed（ICMP 回程被拦或对端静默），
所以 **UDP 13401 是否存在服务无法用当前手段判定**。这也是 §5 的待办之一。

## 5. 残余可能（按可能性排序）

1. **桥处于"未开启"状态（当前主解释）**：listener 是"门"而不是"桥"；`accept→close` 是未开桥时的表现。
   开桥例程若存在，应在 `0x1220`（唯一实现 `0x31` 的节点，`27/31` 被安全门锁死）或 DoIP 之外的凭据链上。
   判据：开桥动作之后，13401 应出现"不立刻 FIN"或"回帧"；用 `04_SOLVE/cgw/watch_bridge.py` 监测。
2. **源 IP 白名单**：若 listener 只对内部网段（如 10.229.221.0/24、10.226.193.0/24、10.224.139.0/24）放行，
   外部客户端永远被 close。TCP 层无法伪造源 IP 完成三次握手（SYN-ACK 会发给被伪造地址），除非有内网跳板。
3. **真实桥进程已死 / 被 TCP wrapper 接管**：listen socket 仍在（TCP 能建连），但 app 逻辑不处理即 close。
4. **UDP 侧**：见 §4，需要能收到 ICMP 或在内网侧抓包才能判定。

## 6. 给团队的建议

- **不要把 13401 当"协议题"**：从外部 vantage 它当前不可交互，且没有任何客户端可调参数能改变其行为（read 从未发生）。
  它是"关着的门"，价值在**开桥例程**而不是协议猜测。
- 开桥例程只可能在：①`0x1220` 的 `0x31`（被安全门锁，需外部凭据）；②DoIP 之外的凭据链（TSP/T-BOX/OTA 工程包）；
  ③另一个主机/端口的控制面。
- **开桥后如何第一时间发现**：`python 04_SOLVE/cgw/watch_bridge.py 10.226.193.2` 每 10 s 一次
  connect-only（1.2 s 观察窗），一旦出现"不立刻 FIN / 收到任意字节"即打印 `STATE_CHANGE` 并退出。
  已验证：当前状态稳定输出 CLOSED（FIN ~26 ms）；2026-11-14 10:03–10:23 连测 **119 次全部 CLOSED**（`0522`），
  之后的 60 min 长监测在 `0535`。
- 复核用 `04_SOLVE/cgw/retest_after_vpn.py`（<=40 连接）即可，不做全端口 blast（见 §7）。

## 7. 风险与教训

- 09:44–09:48 我方对旧 .2 做了 2 轮 x65535 SYN 的 scapy blast（~500 pkt/s，共 ~131 s）；09:51 旧 IP 全部不可达。
  **后经 cgw-doip 确认这是靶场重启迁移到 10.226.193.2，不是被封**（OpenVPN 在 09:56 也发生了一次重连，
  不排除隧道短暂中断）。教训：blast 本身无收益（nmap/慢扫已给过端口表），以后一律低频/定向。
- 抓包教训：`sniff()` 必须在建连**之前**启动并等其就绪（首次实验因 join 后才 sniff，捕到 0 包），
  且 TAP 接口必须用 `\\Device\\NPF_{GUID}` 路径。
- 用 socket `recv()` 判 FIN/RST 会被"数据与 FIN 赛跑"误导；判"服务端是否读过数据"必须用
  **把数据放进第三个 ACK** + 抓包看 `A(a=seq+len)` 后紧跟 `R` 的序列。
- 环境会重启换 IP（VIN 也变）：结论必须绑定"实例 + 时间 + IP"，并在新实例上复现一次才算数。
