# 99_DEAD/ecu-proxy —— 「CGW 8080 是到 ECU 子网的正向代理」已证伪

- 日期：2026-11-14 09:35 CST
- 提出者：lead
- 假设：10.224.139.5/6/7 不可直达，但 10.230.164.4:8080（=10.229.221.2，中央网关）可能是一个
  HTTP 正向代理 / 反代，把请求转发到 ECU 子网。

## 判据（先写）
若 8080 是正向代理，则发 absolute-URI 请求
`GET http://10.224.139.6:8080/healthz HTTP/1.1` 到 8080，
响应应当来自 **10.224.139.6**（即 ECU 的 `/healthz`），而不是本机 8080 的 `/healthz`。
更强判据：发 `GET http://10.224.139.6:8080/graphql`（ECU 上没有此路由），
若代理真的转发，响应应由 ECU 产生（404）；若只是本地路径匹配，则由本地路由表决定。

## 实测结果

| 主机 | URI | 期望（若为代理） | 实际 |
|---|---|---|---|
| 10.230.164.4 | `http://10.224.139.6:8080/healthz` | ECU 的 healthz | `200` + `{"status":"ok"}` |
| 10.230.164.4 | `http://10.224.139.6:8080/graphql` | 404（ECU 无此路由） | **404 page not found** |
| 10.230.164.4 | `http://10.224.139.6:8080/nonexistent` | 404 | 404 |
| 10.230.164.2 | `http://10.224.139.6:8080/graphql` | 404 | **405 method not allowed**（= .2 自己的 /graphql 路由） |

关键证据是最后一行：把 URI 的 host 换成 ECU，路径 `/graphql` 在 `.2` 上仍然命中了
`.2` **自己**的 graphql 处理器并返回它自己的 405。这说明 Go `net/http` 只从
absolute-URI 里取了 `URL.Path` 做本地 mux 匹配，**Host 部分被完全忽略**。

## 结论：DEAD

8080 不是代理，不存在从 CGW 应用层转发到 ECU 子网的通道。
`CONNECT 10.224.139.6:8080` 在四台 8080 上全部返回 `404 Not Found`（Go 的 CONNECT 未注册 → 404），
进一步排除隧道假设。

## 回到这条路的入口
若将来怀疑 ECU 子网可达，不要去试 8080 代理；直接测 L2/L3：
- UDP 13400 DoIP Vehicle Identification Request 到 `10.224.139.6`（UDP 可能未被过滤）
- UDP 任意端口拿 ICMP port-unreachable（证明主机存活、仅端口关闭）
这两条已写进 `ecu-reach` 的清单（看板卡 `a96ae0a1`）。
